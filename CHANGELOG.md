### Step 4.5 - pre-tag closure of the Step 4 audit findings

- F1 (IP-1): Base64 joining in `app/inspection.py` now tries contiguous runs of adjacent candidates longest first from each position, so one neighbouring 20+ character word (or path) no longer makes the whole-group join fail and leaves the split payload undecoded. The first version of this fix capped runs at `MAX_JOIN_TOKENS = 16` (`BUNDLE_ALGORITHM_REVISION = 2`); that cap introduced the R1 regression below and was removed in Step 4.6. Revision 2 never left the working tree.
- F2 (TM-R6): the app is built with `redirect_slashes=False`; `POST /v1/chat/`, `GET /healthz/` and `POST /v1/chat//` get the uniform 503 instead of a 307 redirect.

### Step 4.6 - R1 regression in joined Base64 decoding

- R1 (IP-1, TM-R1, TM-R2): capping joined runs at 16 pieces let a payload split into more than 16 pieces fall off a 4-character block boundary at piece 16, decode only its prefix, and misalign every remaining piece, hiding the end of the payload (52/300 English and 63/300 Arabic trials in the audit). Re-decoding every longer run from every start without a cap fixed that but cost about 110 ms on 181 junk candidates in 4,000 characters.
- Resolution: joined runs now use incremental forward-scan decoding with no 16-piece cutoff. From each start, Base64 (and hex) decode only newly completed blocks into a strict incremental UTF-8 decoder, so no token is re-decoded as part of a longer run; a start stops scanning as soon as its bytes are not UTF-8, a token breaks the encoding rules (`=` before the end), or the 85% printable ratio can no longer be reached even if every remaining character were printable. The longest valid run wins. A stop inside a group must end on a block boundary or `=` padding, so the tokens after it start on a fresh block; when no such stop exists the longest run is used anyway, and its continuation is joined without the whitespace gap (an unpadded payload next to an ordinary word would otherwise be left undecoded or split mid-word).
- `MAX_JOIN_TOKENS` is removed. `BUNDLE_ALGORITHM_REVISION` is now 3 and the `bundle_version` payload carries `join_scan = "incremental-uncapped"` in its place, so every IP-5 layer cache key built from an earlier bundle is invalidated.
- Measured (fixed seeds 0 to 299, payloads of 520+ characters split into random 20 to 27 character pieces, more than 16 pieces): 0/300 hidden in each of English without a decoy word, English with a leading or trailing decoy word, Arabic without a decoy word, and Arabic with a leading or trailing decoy word; also 0/300 with padding stripped. Worst case on 181 candidates in 3,800 characters: 1.1 to 1.7 ms for random junk and 4.1 to 6.9 ms for valid UTF-8 non-printable tokens (best of 20 calls, range over several runs on one developer machine), against the 400 ms TM-R2 budget. The worst case is bounded by the pruning rule, not by a piece limit; `tests/test_inspection.py` asserts the scan work rather than wall-clock time: at most 6,000 token feeds on both floods above (against about 16,400 for the naive design), and at most 16,000 on the near-threshold flood below.
- Note (Step 5A, closes audit finding L1): the scan work is quadratic in the worst case, not linear, so the Step 4.6 test name and this entry overstated it. The worst case is a near-threshold flood: 190 identical 15-byte tokens, each with 3 non-printable bytes (20% non-printable against the 15% the 85% rule allows), keep every start alive for most of the run. Measured: 13,913 token feeds against 18,145 for the naive uncapped design (about 77%); 21 to 26 ms on one developer machine against about 1.3 s for the naive re-decode (the audit measured about 13 ms against about 346 ms), well inside the 400 ms TM-R2 budget. The test is renamed `test_scan_work_is_pruned_on_hostile_candidate_floods`, and `test_scan_work_is_quadratic_but_bounded_on_a_near_threshold_flood` asserts the 16,000-feed bound. No code change, `BUNDLE_ALGORITHM_REVISION` stays 3, and `bundle_version` is unchanged.

## [Unreleased] - Step 5B (full cascade: L2, L3, X3, shadow tiers, IP-7 pool)

No frozen W2 interface changed: `contracts/` is untouched. The `IngressLayer` protocol is unchanged; `PinnableLayer`, `TightenableLayer`, `Deadline` and `LayerBudgetExceeded` in `app/layers/base.py` are additive. Shadow modes log the frozen `ShadowRecord` and `EgressVariantRecord` as specified.

- L2 (`app/layers/l2_threat_memory.py`, `app/vector_store.py`, `app/onnx_models.py`): `all-MiniLM-L6-v2` ONNX (mean pooling, L2 normalized) on the bundle's `minilm` plan (256 tokens), max cosine to the nearest record of the pinned ChromaDB collection version over every window of both views; block at `L2_THRESHOLD` (0.80, a default until validation tuning). Versions are immutable and content-addressed; the active-version pointer is swapped atomically (`os.replace` after fsync, then one reference assignment) and read once per request through `pin()`. `harden_threat_memory()` builds a new version (parent plus new windows of both views) and swaps the pointer, which invalidates cached L2 verdicts through the `chroma_version` in the IP-5 key. ChromaDB anonymized telemetry is off. Startup refuses L2 without an active version.
- L3 (`app/layers/l3_classifier.py`): off-the-shelf `protectai/deberta-v3-base-prompt-injection-v2` ONNX export on the bundle's `deberta` plan (512 tokens), max malicious probability (softmax of the `INJECTION` label read from `config.json`), block at `L3_THRESHOLD` (0.50). `L3_MODEL_DIR` swaps in a fine-tuned export; the artifact hashes are part of the layer version.
- IP-2: both layers register their real tokenizer limits, so sub-window splitting runs before the 16-window cap; splits are logged (`IP-2 sub-window split (not truncation)`), `truncation_count` stays 0, and a view above 16 windows after splitting for any layer is `Blocked-ingress` / `window_cap` with the uniform 503. Measured on the real tokenizers: random spaceless Base64 is about 426 MiniLM tokens and 441 DeBERTa tokens per 600 characters (split for MiniLM only); `!` padding is 602 tokens for both (MiniLM 3 pieces, DeBERTa 2), so 4,000 characters of it exceed 16 MiniLM sub-windows. MiniLM's WordPiece maps any spaceless run above 100 characters without punctuation to one `[UNK]` token, so such runs never need a split but are also opaque to L2 (L3's SentencePiece tokenizer still sees them).
- IP-7 (`app/executor.py`): bounded pool, `LAYER_POOL_WORKERS` (0 means one per physical core, `psutil`) plus `LAYER_POOL_QUEUE_LIMIT` (32) outstanding calls; one more is shed at once as `Error` / `load_shed` with the uniform 503. Bundle builds and L1 to L4 all run there; a slot frees only when its call returns, so timed-out calls keep occupying the pool (E4 reports saturation through `PoolStats`). L2 and L3 also stop between windows once their TM-R2 budget is spent, which frees the thread early; the partial scores are discarded.
- TM-R3: P-degrade now re-decides every completed L2 result with the threshold lowered by `P_DEGRADE_THRESHOLD_DELTA` when another layer faulted, in addition to running later layers tightened; with no completed layer it behaves as P-closed. Tightened verdicts are never cached. Startup warm-up runs past a budget without failing (budgets are per request).
- X3 (`app/layers/l4_egress.py`): X2, then the decoded-text scan of the masked content (NFKC, `Cf` strip, Base64/hex depth 2, the ingress decoder) where any finding blocks, then the leak check against the registered system prompt: MiniLM similarity >= 0.80 or word 3-gram overlap >= 0.30 blocks [Project Decision: the O1 oracle defaults]. Reasoning gets the same checks, logged only. `L4_REVISION` is 2, so egress cache rows from Step 5A no longer match.
- IP-4 (`app/pipeline.py`, `app/audit.py`, `app/routes.py`): `shadow_ingress_only` runs L1, L2, L3 with no short-circuit and zero Groq calls and logs one `ShadowRecord`, releasing nothing; `shadow_full_e2e` also calls the target (or its cache) for every item and logs X0 to X3 as `EgressVariantRecord`s on the same response; its client-visible response is what the production cascade would release under `EGRESS_VARIANT` and `TIMEOUT_POLICY` [Project Decision]. Each variant's output is returned in-process for harness oracles and never logged. Both tiers require L2 and L3 enabled.
- Settings (`app/config.py`, `.env.example`): `L2_ENABLED`, `L3_ENABLED`, `MINILM_MODEL_DIR`, `L3_MODEL_DIR`, `L3_MALICIOUS_LABEL`, `CHROMA_DB_PATH` (synced-folder check, IP-8), `L2_THRESHOLD`, `L3_THRESHOLD`, `X3_SIMILARITY_THRESHOLD`, `X3_NGRAM_OVERLAP_THRESHOLD`, `X3_NGRAM_SIZE`, `LAYER_POOL_WORKERS`, `LAYER_POOL_QUEUE_LIMIT`. `EGRESS_VARIANT=X3` and the shadow modes are no longer refused.
- Artifacts and scripts: `scripts/fetch_models.py` downloads the two models at fixed commits and verifies SHA-256 (recorded in `docs/artifacts.md`; `tests/test_artifacts.py` keeps both identical); `models/` is git-ignored and skipped by the PS-5 linter (third-party tokenizer vocabularies contain emoji and dashes as data). `scripts/build_l2_collection.py` builds or extends a collection version from JSONL; `data/l2_seed/bootstrap.jsonl` (24 hand-written lines) is a development and demo seed only, not experiment data. `scripts/latency_check.py` measures single-request p50/p95.
- PS-2: the attacker isolation guard also forbids paths into `data/chroma_db` (DB contents are secret from the attacker, §1.3).
- Dependencies: `chromadb`, `onnxruntime`, `tokenizers`, `psutil` added to `requirements.in`; `requirements.txt` re-pinned with every existing pin kept (Python 3.11, Windows).
- Measured CPU cost (one developer machine, Intel Family 6 Model 140, 4 physical cores, one ONNX thread per call): see `scripts/latency_check.py` output in the Step 5B report. With the default budgets, the off-the-shelf DeBERTa-v3-base exceeds the 150 ms L3 budget on prompts longer than about one sentence and MiniLM exceeds the 50 ms L2 budget on multi-window prompts, so TM-R3 decides those requests from the completed layers.
